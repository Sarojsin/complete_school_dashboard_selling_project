# Dual Portal System Implementation Plan
## School Portal & College Portal Separation

---

## 📋 Executive Summary

Implement a dual-portal architecture that completely separates **School** and **College** user experiences. Users will select their portal type on the landing page, log in through their respective portal's authentication, and be restricted to only their portal's dashboards and data throughout their session.

**Current State:**
- Landing page already presents "School System" and "College System" options
- Frontend has 2 college modules (teacher, placement) and 14 school modules
- Backend has separate `/api/v1/school/*` and `/api/v1/college/*` endpoints
- User model lacks `portal_type` field → no portal separation enforced
- College modules are 75% less implemented than school modules
- All routes currently accessible to any authenticated user regardless of portal

**Target State:**
- Distinct portal selection → login → dashboard flow
- Complete isolation: school users cannot access college routes/data and vice versa
- Role-based routing within each portal context
- Portal-specific UI theming and navigation
- Backend validation at every endpoint level

---

## 🏗️ System Architecture

### Portal Types
| Portal | Routes Prefix | Modules | Roles |
|--------|--------------|---------|-------|
| **School** | `/` (no prefix) | 14 modules | student, teacher, parent, authority, hod, exam_section, account_section, library_manager, super_admin |
| **College** | `/college` | To be expanded (currently 2 modules) | faculty, student, hod, dean, registrar, exam_section, account_section, placement, research, hostel, lab, etc. |

### Key Principle
**Portal type is immutable and determined at user creation**. A user belongs to ONE portal system for their entire lifecycle. Cross-portal access is forbidden at both frontend (UI routing) and backend (API dependency) layers.

```python
from modules.shared.models import PortalType

def require_portal(expected_portal: PortalType):
    """
    Dependency factory to ensure user belongs to the expected portal.
    Use for routes that are portal-specific.
    """
    def checker(current_user: User = Depends(get_current_user)):
        if current_user.portal_type != expected_portal:
            from modules.shared.exceptions import ForbiddenError
            raise ForbiddenError(
                f"This resource belongs to the {expected_portal} portal. "
                f"Your account is registered under the {current_user.portal_type} portal."
            )
        return current_user
    return checker

# Convenience dependencies
require_school_portal = require_portal(PortalType.SCHOOL)
require_college_portal = require_portal(PortalType.COLLEGE)
```

```javascript
export const login = async (username, password, portalType = null) => {
  const payload = { username, password };
  if (portalType) {
    payload.portal_type = portalType;  // SEND to backend
  }
  
  const response = await api.post('/auth/login-json', payload);
  
  if (response.data.access_token) {
    localStorage.setItem('access_token', response.data.access_token);
    localStorage.setItem('token', response.data.access_token);
    
    // Store full user data including portal_type
    const userData = response.data.user;
    localStorage.setItem('user', JSON.stringify(userData));
    localStorage.setItem('portal_type', userData.portal_type);  // NEW: store separately for easy access
  }
  return response.data;
};

export const getCurrentUser = async () => {
  const response = await api.get('/auth/me');
  return response.data;
};
```

```javascript
import React from 'react';
import { Navigate, useLocation } from 'react-router-dom';

const PrivateRoute = ({ 
  children, 
  allowedRoles = null, 
  allowedPortal = null,  // NEW: restrict by portal type
  redirectTo = '/login' 
}) => {
  const token = localStorage.getItem('access_token');
  const userJson = localStorage.getItem('user');
  const location = useLocation();

  if (!token) {
    return <Navigate to={redirectTo} state={{ from: location }} replace />;
  }

  let user = null;
  try {
    user = userJson ? JSON.parse(userJson) : null;
  } catch (e) {}

  if (!user) {
    return <Navigate to={redirectTo} replace />;
  }

  // NEW: Check portal type restriction
  if (allowedPortal && user.portal_type !== allowedPortal) {
    // Redirect to appropriate portal landing
    const portalDashboard = user.portal_type === 'college' 
      ? '/college/teacher/dashboard'  // or appropriate role-based route
      : '/teacher/dashboard';
    return <Navigate to={portalDashboard} replace />;
  }

  // Existing: Check role restriction
  if (allowedRoles && user.role && !allowedRoles.includes(user.role)) {
    return <Navigate to="/dashboard" replace />;
  }

  return children;
};

export default PrivateRoute;
```

```javascript
const DashboardRedirector = () => {
  const navigate = useNavigate();

  useEffect(() => {
    const token = localStorage.getItem('access_token');
    if (!token) {
      navigate('/login', { replace: true });
      return;
    }

    let user = null;
    try {
      user = JSON.parse(localStorage.getItem('user') || 'null');
    } catch (e) {}

    if (!user || !user.role) {
      navigate('/login', { replace: true });
      return;
    }

    const role = String(user.role).toLowerCase();
    const portal = user.portal_type || 'school';  // NEW: get portal

    if (portal === 'college') {
```


**Option B (unified):** Single endpoint with portal_type in request body.

**Recommendation: Option A** - maintains separation, easier to secure, explicit.

## ⚡ Phase 8: Backend API Changes Detail

### 8.1 User Model Migration SQL (Direct)

```sql
-- Step 1: Add portal_type column (nullable)
ALTER TABLE users ADD COLUMN portal_type VARCHAR(20);

-- Step 2: Infer portal_type from existing profile data
-- School users: have entries in school_* tables
UPDATE users u
SET portal_type = 'school'
WHERE EXISTS (
  SELECT 1 FROM school_student s WHERE s.user_id = u.id
  OR EXISTS (SELECT 1 FROM school_teacher t WHERE t.user_id = u.id)
  OR EXISTS (SELECT 1 FROM school_parent p WHERE p.user_id = u.id)
  -- ... other school profiles
);

-- College users: have entries in college_* tables
UPDATE users u
SET portal_type = 'college'
WHERE EXISTS (
  SELECT 1 FROM college_students cs WHERE cs.user_id = u.id
  OR EXISTS (SELECT 1 FROM college_faculty cf WHERE cf.user_id = u.id)
  -- ... other college profiles
);

-- Step 3: Make NOT NULL (after verifying all users have portal_type)
ALTER TABLE users ALTER COLUMN portal_type SET NOT NULL;

-- Step 4: Add index for performance
CREATE INDEX idx_users_portal_type ON users(portal_type);
```

## 🎓 Key Decisions Made

1. **Portal prefix in URL:** `/college/*` for college, no prefix for school (root paths stay school)
   - Rationale: Existing school routes already use `/student`, `/teacher` etc; keep those as-is. College gets namespaced subdirectory.

2. **Portal validation location:** Both frontend (UX) AND backend (security)
   - Defense in depth. Frontend blocks navigation; backend blocks API access.

3. **User portal assignment:** Immutable, set at account creation
   - Cannot switch portal; must create new account for other portal

4. **Super Admin access:** Portal-agnostic (can access both /admin and /college/admin if needed)
   - Exclusion from portal checks

5. **Token includes portal_type:** Enables stateless portal validation
   - No DB lookup needed for basic portal check (already getting user from DB anyway)

6. **College routes prefixed:** `/college/portal/dashboard` not `/collegeportal/dashboard`
   - Clean URL structure, mirrors backend `/api/v1/college/*` prefix
